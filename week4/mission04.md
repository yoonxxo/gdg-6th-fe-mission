### 많이 쓰이는 폴더 이름

**`components`**

: 여러 페이지에서 재사용되는 공통 컴포넌트를 모아두는 폴더이다.

예를 들어 버튼, 입력창, 카드, 네비게이션 바, 푸터처럼 여러 화면에서 반복해서 사용되는 UI 요소를 넣는다.

**`pages`**

: 라우팅 단위가 되는 페이지 컴포넌트를 모아두는 폴더이다.

각 URL에 연결되는 화면을 담당한다. 프로젝트가 커질수록 페이지별 코드를 분리하면 관련 코드를 찾기 쉬워진다.

**`hooks`**

여러 컴포넌트에서 재사용되는 커스텀 훅을 모아두는 폴더이다.

예를 들어 검색어 관리, 상품 필터링, 장바구니 로직처럼 컴포넌트에서 분리할 수 있는 로직을 hook으로 만들 수 있다.

단, 특정 페이지에서만 쓰는 hook이면 전역 `hooks`가 아니라 해당 페이지 폴더 안에 두는 것도 좋다.

**`utils`**

: 여러 곳에서 재사용되는 순수 함수들을 모아두는 폴더이다.

포맷팅 함수 같은 유틸리티 기능이 들어간다. (sortItems, filterItems)

**`apis`** 또는 **`services`**

: 서버나 JSON 파일에서 데이터를 가져오는 API 요청 함수를 모아두는 폴더이다.

`fetch`, `axios` 등을 직접 페이지 안에서 쓰지 않고 API 함수로 분리하면 코드가 깔끔해진다.

**`data`**

: 정적인 데이터나 mock 데이터를 모아두는 폴더이다.

처음에는 mock 데이터를 `data`에 두고, 나중에 API 요청 형태로 바꾸면 `apis` 폴더와 함께 사용할 수 있다.

**`assets`**

: 이미지, 아이콘, 폰트 같은 정적 파일을 모아두는 폴더이다.

단, Vite/React에서는 `public` 폴더에 둔 파일도 바로 사용할 수 있어서, 그대로 `public`에 둬도 된다.

**`styles`**

: 전역 CSS나 공통 스타일 파일을 모아두는 폴더이다.

Tailwind를 주로 사용한다면 파일이 많지 않을 수 있다. 그래도 전역 스타일, CSS 변수, reset CSS 등이 있으면 `styles`에 두면 된다.

**`store`**

: Zustand, Redux 같은 전역 상태관리 코드를 모아두는 폴더이다.

장바구니, 검색어, 필터 조건 같은 전역 상태를 여기에 둘 수 있다.

**`constants`**

: 여러 곳에서 공통으로 사용하는 상수값을 모아두는 폴더이다.

```jsx
export const CATEGORIES = ["의류", "전자기기", "화장품", "식품"];
```

카테고리명, 라우트 경로, 버튼 이름처럼 바뀔 가능성이 낮고 여러 곳에서 쓰이는 값을 넣으면 좋다.

**`layouts`**

: 페이지 공통 레이아웃을 담당하는 컴포넌트를 모아두는 폴더이다.

예를 들어 모든 페이지가 `Navbar`, `Footer`를 공통으로 가진다면 `MainLayout`으로 묶을 수 있다. 네비게이션 바, 사이드바, 컨테이너 같은 레이아웃 컴포넌트는 `layouts` 폴더에 둘 수 있다.

**_상황에 따라 폴더구조는 바뀔 수 있으며 정답은 없다._**

### FSD

: React 프로젝트를 **기능(feature) 중심으로 폴더를 나누는 아키텍처 설계 방식**이다.

관련된 컴포넌트, 로직, API 등을 기능 단위로 묶어 관리한다.

상위 계층은 하위 계층에 의존하지 않고, **하위 계층은 상위 계층을 import할 수 없다.**

- 프로젝트의 규모가 커질수록 관리하기 좋다
- 팀 협업 시 역할 분리가 명확하다.
- 관련 코드가 한 곳에 모여 찾기가 쉽다.
- 작은 프로젝트에서는 구조가 다소 복잡할 수 있다.

## 폴더 구조 리팩토링해보기

쇼핑몰 웹페이지 만들기 프로젝트에서 역할에 따라 폴더를 분리해 관리하기 쉽도록 구조를 정리했다.

기존에는 컴포넌트와 페이지, 상태 관리 코드가 명확하게 구분되지 않고 정리가 되지 않은 느낌이었다면, 리팩토링 후에는 역할별로 폴더를 나누었다.

- `pages`
  - 라우팅 단위의 페이지 컴포넌트를 관리
  - (`Home`, `CategoryPage`, `PricePage`, `SortPage`, `AdminPage`)
- `components`
  - 재사용 가능한 UI 컴포넌트를 관리
  - `common`
    - 여러 곳에서 공통으로 사용하는 컴포넌트
    - (`Button`, `Input`)
  - `admin`
    - 관리자 페이지에서 사용하는 기능별 컴포넌트
    - (`ProductRegister`, `ProductAdd`, `ProductDelete`)
- `apis`
  - API 요청 관련 함수 관리
  - (`itemApi.js`)
- `constants`
  - 변하지 않는 상수 데이터 관리
  - (`categories.js`)
- `stores`
  - Zustand를 사용한 전역 상태 관리
  - (`useCartStore.js`)

이렇게 역할별로 구조를 나누니 필요한 파일을 찾기 쉬워졌고, 기능 수정 시 관련 코드의 위치가 명확해져 유지보수가 더 편해졌다고 느꼈다.
